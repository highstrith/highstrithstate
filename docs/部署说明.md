# 部署与发布说明

线上地址：<https://highstrith.github.io/highstrithstate/>
仓库：<https://github.com/highstrith/highstrithstate>

## 一句话版本

改完代码后，**必须让 `main` 前进**才会真正上线；只推 `release/white-pages` 过去是不会发布的。

```bash
# 日常开发（在 worktree：/Volumes/E61--/网站/site-portfolio-upgrade）
git add -A && git commit -m "feat: ..."
git push origin release/white-pages

# 发布上线（关键一步）
git push origin release/white-pages:main
```

`release/white-pages` 通常是 `main` 的后代，这条命令是快进（fast-forward），不会产生合并提交，也不会冲突。如果哪天提示非快进，说明有人在 `main` 上直接提交过，先 `git fetch` 再 `git merge` 处理。

## 部署链路

`.github/workflows/pages.yml` 由 GitHub Actions 执行，触发条件：

- push 到 `main`
- push 到 `release/white-pages`（2026-10-30 新增，避免"推了却没上线"）
- 手动 `workflow_dispatch`（在 Actions 页面点 Run workflow）

工作流只发布一份白名单，**不是整个仓库**：

| 会发布 | 不发布 |
| --- | --- |
| `index.html`、`projects.html`、`in-progress.html`、`resume.html` | `docs/`、`tests/`、`archive/`、`originals/` |
| `assets/`（排除 `assets/originals/`） | 根目录其他 md、`data/` 之外的临时文件 |
| `data/` | |

所以新增资源必须放在 `assets/` 下、新增页面必须加进工作流的 `cp` 列表，否则线上 404。

## 上线后看不到变化怎么办

按这个顺序排查，基本能定位：

1. **确认 workflow 跑过了** —— GitHub 仓库 → Actions → "Deploy GitHub Pages"，看最新一次是不是绿色。红色就看哪一步失败（最常见是 `Prepare site` 里 `cp` 的文件不存在）。
2. **确认线上 HTML 真的变了** —— 不要只看自己浏览器，直接拉源码验证：

   ```bash
   curl -s https://highstrith.github.io/highstrithstate/index.html | grep -o 'theme.js?v=[^"]*'
   ```

3. **清缓存** —— 线上 HTML 是 `cache-control: max-age=600`，浏览器最多会存 10 分钟旧页面。Mac 用 `Cmd + Shift + R`，手机端关掉标签页重开；微信、飞书等内置浏览器缓存更顽固，需要清应用缓存。
4. **确认资源版本号变了** —— 改 CSS/JS 时同步改 HTML 里的 `?v=` 后缀（例如 `?v=20261030-theme`），否则浏览器会沿用旧文件。

## 本次踩到的坑（2026-10-30）

推了 `release/white-pages`，线上毫无变化，原因就是工作流当时只监听 `main`。检查方式：

```bash
git ls-remote --heads origin            # 看远端各分支到底在哪
git merge-base --is-ancestor origin/main origin/release/white-pages && echo 可快进
```

现在已经把 `release/white-pages` 也加进触发分支，同类问题不会再出现。代价是：**这个分支上的提交会直接上生产**，所以不要在 `release/white-pages` 上交半成品。

## 并发行为：连续推两个分支会取消前一次

工作流配了 `concurrency: group: pages, cancel-in-progress: true`，意味着同一时间只保留一个部署。如果像上面那样先推 `release/white-pages` 再推 `main`，会出现：

| 运行 | 分支 | 结果 |
| --- | --- | --- |
| #36 | `release/white-pages` | cancelled（被 #37 顶掉） |
| #37 | `main` | success |

第一次显示 `cancelled` 是**正常现象**，不是失败——后一次部署的内容更完整，会覆盖前一次。只要最新一次是绿色就算上线成功。

只推一个分支时不会出现这个问题。
