# 部署与发布说明

线上地址：<https://highstrith.github.io/highstrithstate/>
仓库：<https://github.com/highstrith/highstrithstate>

## 一句话版本

改完代码后，**必须让 `main` 前进**才会真正上线；只推 `release/white-pages` 过去是不会发布的。

```bash
# 日常开发（在 worktree：/Volumes/E61--/网站/site-portfolio-upgrade）
git add -A && git commit -m "feat: ..."
git push origin release/white-pages

# 发布上线（关键一步）
git push origin release/white-pages:main
```

`release/white-pages` 通常是 `main` 的后代，这条命令是快进（fast-forward），不会产生合并提交，也不会冲突。如果哪天提示非快进，说明有人在 `main` 上直接提交过，先 `git fetch` 再 `git merge` 处理。

## 部署链路

`.github/workflows/pages.yml` 由 GitHub Actions 执行，触发条件：

- push 到 `main`
- push 到 `release/white-pages`（2026-10-30 新增，避免"推了却没上线"）
- 手动 `workflow_dispatch`（在 Actions 页面点 Run workflow）

工作流只发布一份白名单，**不是整个仓库**：

| 会发布 | 不发布 |
| --- | --- |
| `index.html`、`projects.html`、`in-progress.html`、`resume.html` | `docs/`、`tests/`、`archive/`、`originals/` |
| `assets/`（排除 `assets/originals/`、`assets/works/`、`assets/uploads/`） | 源文件母版：`assets/works/*.mp4`、`assets/uploads/**/*.mp4` |
| `assets/uploads/` 中除 `*.mp4` 外的文件（海报、二维码等） | `server/`、`scripts/`、`serve.js`、`admin.html`、`admin.css` |
| `data/` | 根目录其他 md、`tmp/` 临时文件 |
| `reel/index.html`（只有一张跳转页，见下） | 橘生梦厂的源码、封面、片库 —— 那是另一个仓库 |

2026-10-30 起把**源文件母版排除出发布**：每个作品都会生成 `preview / mobile / web` 三档派生视频，页面只引用这三档；源文件只用于重新转码，留在 git 里但不上线。发布体积因此从 1.27GB 降到约 310MB（低于 GitHub Pages 的 1GB 站点上限）。

所以新增资源必须放在 `assets/` 下、新增页面必须加进工作流的 `cp` 列表，否则线上 404；新增作品后要跑一次 `node scripts/optimize-media.mjs` 生成派生视频，否则页面只能回退到源文件（而源文件不上线）。

## 和橘生梦厂的关系：两个仓库，一个链接

橘生梦厂是**独立站点**，源码、脚本、测试、文档都在 <https://github.com/highstrith/jusheng>，发布到 <https://highstrith.github.io/jusheng/>。本仓库不再包含它的任何代码，只保留两样东西：

1. `index.html` 里的入口链接（绝对地址、`target="_blank"`）和三张推荐封面 `assets/film-recommendation/`；
2. 产物里的 `public/reel/index.html` —— 一张 `<meta http-equiv="refresh">` 跳转页，让早前分享出去的 `/reel/` 链接不至于变成 404。**不要往这个目录里放别的文件**，否则等于双发布，`tests/pages-artifact-integration.mjs` 会直接报错。

要改片单、封面、页面，去 jusheng 仓库改，那边有自己的 `scripts/ship.sh`。


## 视频编码策略

`scripts/optimize-media.mjs` 生成三档，参数在文件顶部的 `profile` / `webProfile` 里：

| 档位 | 用途 | 参数 | 典型体积 |
| --- | --- | --- | --- |
| `preview` | 首屏与卡片静音预览 | 20s、960px、650k | ~1.7MB |
| `mobile` | 手机 / 粗指针设备点开播放 | 960×540、CRF 27、maxrate 750k | 2–12MB |
| `web` | 桌面点开播放 | 长边≤1920、CRF 23、maxrate 3500k | 1–32MB |

`web` 用独立的 `webProfile` 计算哈希：**调整桌面档参数不会让已缓存的 preview / mobile 失效**（改生成器文件本身仍会让全部失效，因为 `generatorHash` 参与哈希）。

历史上传的源文件码率极高（720p 写到 10–15 Mbps），2026-10-30 重编码后 `web` 合计从 624MB 降到 160MB，单部最大从 90.8MB 降到 31.6MB，SSIM 0.988（与传统 `-c copy` 直传肉眼无差）。

## 上线后看不到变化怎么办

按这个顺序排查，基本能定位：

1. **确认 workflow 跑过了** —— GitHub 仓库 → Actions → "Deploy GitHub Pages"，看最新一次是不是绿色。红色就看哪一步失败（最常见是 `Prepare site` 里 `cp` 的文件不存在）。
2. **确认线上 HTML 真的变了** —— 不要只看自己浏览器，直接拉源码验证：

   ```bash
   curl -s https://highstrith.github.io/highstrithstate/index.html | grep -o 'theme.js?v=[^"]*'
   ```

3. **清缓存** —— 线上 HTML 是 `cache-control: max-age=600`，浏览器最多会存 10 分钟旧页面。Mac 用 `Cmd + Shift + R`，手机端关掉标签页重开；微信、飞书等内置浏览器缓存更顽固，需要清应用缓存。
4. **确认资源版本号变了** —— 改 CSS/JS 时同步改 HTML 里的 `?v=` 后缀（例如 `?v=20261030-theme`），否则浏览器会沿用旧文件。

## 本次踩到的坑（2026-10-30）

推了 `release/white-pages`，线上毫无变化，原因就是工作流当时只监听 `main`。检查方式：

```bash
git ls-remote --heads origin            # 看远端各分支到底在哪
git merge-base --is-ancestor origin/main origin/release/white-pages && echo 可快进
```

当时临时把 `release/white-pages` 也加进过触发分支，后来（分站之后）又收回去了：**现在只监听 `main`**。在 `release/white-pages` 上提交不会上线，必须再推一次 `main`。

## 部署失败时不要点「Re-run failed jobs」（2026-11-04 踩到）

`Deploy to GitHub Pages` 报这个错：

```
Error: Multiple artifacts named "github-pages" were unexpectedly found for this workflow run. Artifact count is 2.
```

看着像 GitHub 抖动，其实是被自己点坏的。`upload-pages-artifact` 产出的产物名固定为 `github-pages`；点「Re-run failed jobs」只会重跑失败的那步之后的部分，**上传那步会再跑一遍，于是同一次运行里堆出第二个同名产物**，`deploy-pages` 一旦查到两个就直接报错。再点一次就变三个，这里永远好不了。

正确做法是开一次**全新的运行**，让产物列表从零开始：

```bash
# 在 Actions 页面点「Run workflow」，或者：
TOKEN=$(printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^password=//p')
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Accept: application/vnd.github+json" \
  "https://api.github.com/repos/highstrith/highstrithstate/actions/workflows/pages.yml/dispatches" \
  -d '{"ref":"main"}'
```

判断是哪种失败：点进失败的那次运行，看 `Deploy to GitHub Pages` 的日志。报 `No artifacts named "github-pages"` 是真的没传上去（可以整跑一次）；报 `Multiple artifacts` 就是被重复运行弄脏了（必须新开一次运行）。

## 并发行为：连续推两个分支会取消前一次

工作流配了 `concurrency: group: pages, cancel-in-progress: true`，意味着同一时间只保留一个部署。如果像上面那样先推 `release/white-pages` 再推 `main`，会出现：

| 运行 | 分支 | 结果 |
| --- | --- | --- |
| #36 | `release/white-pages` | cancelled（被 #37 顶掉） |
| #37 | `main` | success |

第一次显示 `cancelled` 是**正常现象**，不是失败——后一次部署的内容更完整，会覆盖前一次。只要最新一次是绿色就算上线成功。

只推一个分支时不会出现这个问题。
